# Application integration refactor

## Scope and inspected baseline

Requested 2026-10-19: preserve Reader, Atlas, Planner and Safari data while
integrating optional decoded Adventure Profiles and a separate reference Pokédex.
Only SoulSilver/Generation IV is implemented; future games require explicit data.
Work starts on `feature/adventure-integration` from `bf19e35` (v0.25.52).
All 78 existing automated checks passed before implementation, including Chromium
Reader/Planner/Atlas regressions. These use synthetic records, not personal saves.

The app uses independent HTML entry points and native JavaScript modules, with
one shared menu/theme component (`js/app-shell.js`). Retain those entry points,
repository-relative URLs, Reader Overview default and existing hash routes.
Do not introduce a framework or separate hosting. Remote HEAD is `main`; no
checked-in Actions workflow exists, so inspect the repository's actual Pages
configuration before publishing. Unfinished integration stays on its feature branch.

## Risks and decisions

- Reader reset currently clears the session snapshot before a replacement is
  validated. Persistent profile records must survive Load Save and invalid files.
  Reader may still show its familiar empty upload view while choosing a file.
- Existing Planner automatically uses a sole PC candidate and loses explicit
  selections on refresh. The requested party-first/manual-PC behavior intentionally
  supersedes that matching policy. Do not overwrite goals or manual progress with
  derived observations.
- Trainer TID/SID is an index, not a unique profile ID. Provide explicit separate
  adventure creation and require selection when matching identities are ambiguous.
  Never silently merge multiple profiles or associate the legacy plan with a trainer.
- Save snapshots must contain decoded data only, with schema/snapshot versions and
  successful-load time. Reject partial records and future schemas; commit profile,
  latest snapshot and active selection atomically. Storage failures leave previous
  records intact and provide a visible warning.
- Reader's registration arrays currently include only its selected Pokédex scope.
  Future Atlas caught markers need full 493-species flags in separate fields, while
  preserving existing Reader count semantics.
- Current Pokémon records expose identity fields but not individual-record checksum
  validity. Add validation information before accepting persistent snapshots; retain
  the current binary decoding behavior for display.
- PC battle HP/status and stored level are unavailable; preserve existing honest
  unavailable labels. Safari layout, objects, aging and Baoba progression are not
  decoded at all. Snapshot fields must explicitly report unsupported Safari data.
- Evolution exports currently download and immediately reload generated bytes.
  **User approved:** retain last loaded-save progress separately; require original
  binary reload before editing a restored profile; exported previews do not update
  the persistent adventure until the exported file is explicitly loaded.
- Existing metadata comes from live PokéAPI and sprites. Its historical typing
  helper is reusable, but modern abilities, stats, tutor/TM/egg moves, held-item
  probabilities and evolution requirements are not a verified HGSS dataset.
  Acquire pinned sources and document coverage before claiming reference completion.
- Existing non-Safari audits cover the current 69 location groups, not all Kanto.
  Retain their evidence/limits; new Pokédex location coverage must label omissions.
- Cross-tab loads, rapid replacements, reset during restoration and denied storage
  need explicit tests; stale asynchronous work must not restore old UI state.

## Milestone 1 implementation and remaining limits

`js/adventures.js` owns schema-v1 IndexedDB stores for profiles, planners and
settings. A non-unique game/TID/SID index locates candidate profiles; internal UUIDs
keep profile and planner identities independent. Profile/snapshot replacement and
active selection share one transaction. Snapshot validation rejects incomplete
PC slots, corrupt individual checksums, unsupported games/versions, invalid
identities/training/moves and inconsistent registration counts. Older concurrent
loads cannot replace newer stored snapshots. No binary bytes or save offsets are
persisted. The parser now reports individual checksums and incomplete party counts
without changing decoded field values or existing block detection behavior.

Reader uses the same rendering function for fresh decoding and restored data.
Load Save resets the visible Reader but preserves persistent profiles and the
last valid Planner snapshot. Invalid files preserve stored adventures; Open
adventure restores one without reparsing. Explicit profile selection handles
ambiguous trainer identities. Storage-denied sessions still support Reader.

Legacy migration is an idempotent transactional copy of the original v1 JSON and
its exact raw string, not an active Planner storage switch. It neither deletes nor
rewrites the original key nor associates Mando with a newly loaded trainer. The
multi-plan UI/goal model and applying post-migration edits are milestone 2.

That description records the v0.25.53 foundation. Milestone 2 activates the latest
legacy browser state into independent schema-2 planners; the preserved original
key and original/activation migration copies remain unchanged afterward. See the
Planner document for current migration/import behavior.

There are no supported Safari snapshot values yet. PC current HP, battle stats and
status remain unavailable. The parser's scoped Pokédex arrays are preserved;
Atlas-wide caught flags are milestone 3. Existing raw 512 KB input requirements
remain; this milestone does not add emulator-container decoding.

### Real-save acceptance checklist

1. Confirm v0.25.53 at the existing Reader URL. Load a known raw SoulSilver save
   and compare trainer, Party, PC, Seen/Caught and Collection with the game.
2. Refresh. Confirm the same values restore, the Reader starts on Overview, and
   no binary file is needed. Check Party/PC details, both themes and a phone width.
3. Load a newer save. Refresh and verify the latest decoded values remain. Try an
   invalid file; use Open adventure and confirm the last valid snapshot survived.
4. Verify existing Planner checklists and exported v1 backups still work. Profiles
   must not replace desired goals or assign the Mando plan to a trainer.
5. Use separate-adventure creation to preserve a second profile; load a matching
   identity and confirm the explicit choice. Switch back and check both profiles.
6. In a restored eligible Pokémon's detail, confirm the original-save reload note.
   Reload the original binary, export an evolution, and confirm displayed/stored
   progress changes only if the generated file is explicitly loaded. Actual evolved
   save behavior in-game remains unverified.
7. Visit Atlas/EV Training and Planner from Reader; return via Load Save. Confirm
   the GitHub Pages repository path, map/floor navigation and encounters.

Publication and user validation must be updated from observed results;
constructed-save checks are not evidence of real-game validation.
